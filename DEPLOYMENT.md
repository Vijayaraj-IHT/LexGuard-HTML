# LexGuard Phase-1 Deployment Runbook

## Target topology (free / low-cost)

LexGuard Phase 1 deploys as **one Render Python web service** backed by
**Neon PostgreSQL**:

- FastAPI serves the API under `/api/v1`.
- The same FastAPI process serves the zero-build HTML frontend at `/` when
  `SERVE_FRONTEND=true`.
- Keeping browser and API on the **same origin** is deliberate: the Phase-0
  browser session uses an HttpOnly cookie plus a CSRF double-submit cookie.
  A separate static-site origin would need cross-site cookie exceptions.
- `backend/requirements-prod.txt` intentionally excludes
  `torch`/`transformers`. Search and drafting use deterministic fallbacks on
  the free instance; install `backend/requirements-ml.txt` only on a local
  workstation or a paid/GPU host.

The committed corpus PDFs under `backend/storage/cases/` are deployed with the
service and can be served read-only. **Render free disks are ephemeral**:
new uploads made on a free instance can disappear on restart/redeploy. A real
court/production deployment still needs a paid persistent disk or object
storage before accepting uploads as durable records.

## 1. Prepare Neon PostgreSQL

1. Create a Neon project/database. Choose the region closest to the Render
   service (the Blueprint uses Render `singapore`, so Neon Singapore /
   `ap-southeast-1` is the natural pairing).
2. Restore the canonical dump (278 cases / 1,393 legacy audit rows). The
   dump stores embeddings as JSON, matching the backend default
   (`USE_PGVECTOR=false`); native pgvector is an opt-in only for fresh
   databases created with a `vector(384)` column.

   ```bash
   psql "$NEON_DATABASE_URL" -f database/database_dump.sql
   ```

3. Copy Neon's **pooled** connection string for use as `DATABASE_URL` in
   Render. Plain `postgres://` and `postgresql://` URLs are accepted by the
   backend and normalized to SQLAlchemy's psycopg2 dialect.

## 2. Deploy the Render Blueprint

1. In Render, create a new Blueprint from this repository. Render reads
   [`render.yaml`](render.yaml).
2. When prompted, set:
   - `DATABASE_URL` — the Neon pooled connection string from step 1.
   - `ANTHROPIC_API_KEY` — optional; leave blank to use deterministic mock
     drafting (`USE_MOCK_LLM=true`).
3. `SECRET_KEY` is generated by Render (`generateValue: true`). Do not reuse
   the development example secret.
4. The start command is `bash backend/start.sh`. With
   `RUN_MIGRATIONS=true`, each boot first runs the idempotent
   `backend/migrate_phase0.py` (adds `audit_logs.seq`/`segment`, partial
   unique indexes, `cases.judicial_seal`, and converts audit foreign keys to
   `ON DELETE RESTRICT`) and then starts Uvicorn on `$PORT`.

## 3. Perform the disclosed audit reseal (senior action)

The shipped legacy audit chain is **invalid as restored** (first broken link
at replay index 31). The migration preserves it unchanged as segment 0; it
does **not** rewrite hashes. After the first successful deploy, an active
`senior_staff` operator must append the disclosed reseal event, either from
the Admin workstation (**Audit Ledger → Reseal (Senior)**) or by CLI against
the same database:

```bash
cd backend
DATABASE_URL="$NEON_DATABASE_URL" python ../scripts/reseal_audit_chain.py \
  --email staff@lexguard.gov.in \
  --reason "Phase-0 disclosed remediation of legacy audit segment" \
  --confirm
```

Verification should then report the new active segment as valid while still
disclosing archived segment 0 as invalid/superseded.

## 4. Smoke-check the deployment

```bash
curl -fsS https://<service>.onrender.com/health
curl -fsS https://<service>.onrender.com/ready
```

- `/health` is a liveness probe only.
- `/ready` checks the database connection, required Phase-0 schema columns,
  writable storage, and the frontend directory. It returns HTTP 503 with the
  failed check names when the service is not ready.

Then open the service root URL, sign in, run a search, open a case PDF, and —
as senior staff — verify the audit chain segments from the Admin workstation.

## Key environment variables

| Variable | Phase-1 deploy value | Notes |
| --- | --- | --- |
| `ENVIRONMENT` | `production` | Enables production security validation. |
| `SERVE_FRONTEND` | `true` | FastAPI serves `frontend/` same-origin. |
| `RUN_MIGRATIONS` | `true` | Runs the idempotent Phase-0 migration at boot. Set to `false` only after the schema is confirmed if faster cold starts are needed. |
| `COOKIE_SECURE` | `true` | Required outside development. |
| `COOKIE_SAMESITE` | `lax` | Correct for the same-origin topology. |
| `ENABLE_API_DOCS` | `false` | Keeps Swagger/ReDoc off the public demo. |
| `USE_LOCAL_LLM` | `false` | Avoids multi-GB model downloads on free compute. |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` | `3` / `2` | Bounded for one free instance + Neon. |

## Local single-service check

The production topology can be rehearsed locally without the separate static
server:

```bash
cd backend
SERVE_FRONTEND=true DATABASE_URL=sqlite:///./lexguard-local.db \
  python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000/` — the portal, API (`/api/v1`), `/health`, and
`/ready` are all served by the one process. The classic two-server workflow
(static frontend on port 8888 plus API on port 8000) continues to work for
development.

## Free-tier limitations to disclose

- Render free web services spin down after inactivity; the first request after
  idle is slow.
- The free filesystem is ephemeral: treat the deployed corpus as read-only
  and do not rely on new uploads persisting.
- Neon free databases scale to zero; the first query after idle can be slow.
- This topology is appropriate for evaluation/demo use. A production court
  deployment additionally needs durable object storage, backups, monitoring,
  and paid always-on compute.
